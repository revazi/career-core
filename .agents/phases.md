# Phased roadmap

Each phase is a gate. Do not begin implementation from a later phase while the current phase remains incomplete unless the maintainer explicitly changes the roadmap.

## Phase 0 — Repository foundation and agent discovery

### Goal

Create a trustworthy Rust repository that builds cleanly and tells humans and agents exactly what is and is not implemented.

### Scope

- root `career-core` library package
- separate `career` CLI workspace package
- dual MIT/Apache-2.0 licensing
- capability discovery with versioned JSON
- root `AGENTS.md` and detailed `.agents/` handbook
- Agent Skills-compatible project skill
- formatting, linting, tests, build, and CI
- public README, contributing, changelog, and security guidance

### Out of scope

- resume/job domain contracts
- parsing, scoring, or matching
- file ingestion
- LLM or network behavior
- Swift bindings
- crate publication or remote repository creation

### Acceptance

- clean checkout passes all required Rust checks
- `career capabilities` emits valid JSON by default
- only implemented discovery is marked available
- machine output contains no logs or nondeterministic values
- Pi can discover `.agents/skills/career-core/SKILL.md` after project trust
- current documentation is explicit that evaluation and matching are planned

## Phase 1 — Versioned contracts and first resume vertical slice

### Goal

Deliver the first useful deterministic operation through the library and CLI without claiming broad parity.

### Scope

- bounded `ResumeInputV1` accepting plain extracted text and optional caller metadata
- typed `ResumeEvaluationV1`, check, evidence, warning, and error contracts
- integer score range and aggregation rules documented before coding
- explicit source-size, line-count, and line-length limits
- conservative section-header detection for summary, experience, education, and skills
- one explainable section-coverage check cluster
- `career resume evaluate --input <path|-> --format json`
- stdin support and deterministic JSON output
- JSON schemas and synthetic fixtures
- capability `resume.evaluate` becomes available only at phase completion

### Out of scope

- PDF/DOCX extraction
- complete Django scoring parity
- inferred experience details
- job matching
- automatic suggestions generated by AI

### Required reference

- `accounts/services/resume_normalization.py`
- normalization tests and synthetic fixtures listed in `reference-map.md`

### Acceptance

- identical input produces identical typed and JSON output
- malformed/empty/oversized input returns typed bounded errors and nonzero CLI status
- section aliases are explicit and exact; no fuzzy prose matching
- prompt-like source text cannot alter behavior
- scores are bounded and every deduction maps to a check/evidence record
- Linux CI and local verification pass

## Phase 2 — Deterministic resume normalization

### Goal

Produce a bounded structured resume representation with transparent confidence and provenance, plus a provider-neutral boundary for optional source-grounded assistance.

### Scope

- contact, summary, experience, education, skills, projects, and certifications structures
- explicit section alias matching
- conservative experience block parsing
- bounded deterministic fallback heuristics
- parser confidence score, label, and signal breakdown
- field statuses distinguishing detected, likely missing, and not detected
- normalization metadata and warning contracts
- fixture provenance and golden JSON
- Unicode, malformed layout, prose-heavy, and sparse resume coverage
- enrichment eligibility derived only from low deterministic confidence and empty core fields
- versioned provider-neutral proposal, validation, merge, and provenance contracts
- source-grounding validation for every proposed non-empty string
- separate deterministic baseline and assisted document
- `career resume normalize` and `career resume enrich` JSON CLI commands

### Out of scope

- LLM/provider calls, prompt construction, API keys, or network orchestration inside the core or universal CLI
- allowing assisted fields to alter authoritative confidence or scoring
- OCR
- arbitrary document conversion
- format/layout reconstruction
- writing or rewriting resume content

### Required reference

- `resume_normalization.py`
- deterministic portions of resume normalization tests/fixtures
- current normalization metadata versions documented in `reference-map.md`

### Acceptance

- every extracted value is traceable to source text or explicit deterministic transformation
- fallback behavior never overwrites stronger parser output
- confidence remains inspectable and does not become certainty through fallback
- all lists, strings, evidence, metadata, and external proposals are bounded
- non-target, unsupported, malformed, or ungrounded proposed values are rejected without payload-bearing errors
- assisted merging fills only eligible empty fields and preserves the byte-equivalent deterministic baseline
- provider failure can be isolated by a host without losing deterministic output
- golden fixtures cover clean, messy, sparse, adversarial, and source-grounded assisted cases

## Phase 3 — Explainable resume evaluation parity

### Goal

Port the mature deterministic resume checks and aggregation policy without framework coupling.

### Scope

- versioned check catalog and categories
- content, structure, wording, and completeness checks supported by deterministic evidence
- confidence-aware handling of parser uncertainty
- integer category and overall scores with documented aggregation
- strengths, weaknesses, actions, and warnings derived only from checks
- deterministic result fixtures corresponding to Django behavior
- compatibility/difference report for the selected Django policy version
- additive `career.resume_analysis.v1` and `career resume analyze` contracts while preserving Phase 1 evaluation semantics
- authoritative scoring from `resume_normalization_v1` deterministic baseline only

### Out of scope

- LLM interpretation or rewriting
- visual design/layout scoring not supported by extracted text
- opaque ATS claims
- automatic mutation of a resume

### Required reference

- `accounts/services/resume_scoring.py`
- `resume_analysis_response.py`
- deterministic analysis tests and normalization fixtures

### Acceptance

- all checks have stable IDs and bounded evidence
- low-confidence parser gaps are provisional rather than confirmed omissions
- overall/category scores remain in range for every adversarial fixture
- Rust golden fixtures demonstrate declared parity or document intentional differences
- no recommendation contains facts absent from the source/check evidence
- existing `career.resume_evaluation.v1` fixtures remain byte-equivalent
- assisted normalization values cannot enter authoritative analysis

## Phase 4 — Job normalization and conservative matching

### Goal

Compare normalized resume and job evidence deterministically and conservatively.

### Phase 4A sub-gate — Job-description normalization

Scope:

- bounded `JobInputV1` and normalized job contract
- explicit required/preferred skills and qualifications
- responsibilities plus seniority, experience, education, and certification signals
- source spans, field statuses, matched/unmatched metadata, and stable ordering
- six-signal job parse confidence and uncertainty warnings
- `career job normalize` JSON/text CLI command
- clean, prose-heavy, sparse, Unicode, prompt-like, and adversarial fixtures

Out of scope for 4A:

- resume-to-job comparison or score categories
- skill equivalence or recommendation logic
- provider fallback or external-proposal job enrichment
- fetching vacancy URLs

Acceptance for 4A:

- every non-empty normalized value is source-grounded
- explicit sections and inline classifications remain conservative and inspectable
- noise/company/benefit prose cannot create false requirements
- low-confidence fields are unverified rather than confirmed absent
- output lists, diagnostics, evidence, and input are bounded
- selected deterministic fixtures prove declared `job_description_normalization_v6` parity or document differences

### Phase 4B sub-gate — Conservative matching

Begin only after 4A is reviewed and merged.

Scope:

- deterministic category scores, strengths, gaps, and evidence
- exact/alias matching and reviewed same-technology equivalence only
- bounded recommendation policy derived from deterministic gates
- `career job match` JSON CLI command
- tricky fixtures for close-but-non-equivalent skills, vague jobs, and weak resumes

Out of scope for all Phase 4 work:

- fetching vacancy URLs
- embeddings, fuzzy semantic similarity, or LLM equivalence
- company research
- application tracking/persistence
- cover-letter generation

Required reference:

- job normalization, scoring, skill-equivalence, recommendation, prompt-context, and fixture files listed in `reference-map.md`

Acceptance for 4B and Phase 4 completion:

- no adjacent technology is treated as equivalent without explicit policy
- vague/low-confidence job requirements do not become invented hard gaps
- recommendations cannot upgrade deterministic evidence
- all outputs are bounded, explainable, and stable
- CLI consumers can distinguish confirmed, partial, and uncertain findings

## Phase 5 — Agent-ready CLI and distribution

### Goal

Make the deterministic engine dependable from any coding-agent harness through documented local commands.

### Scope

- final command hierarchy and stable exit-code table
- stdin, explicit files, compact JSON, pretty JSON, and human output
- schema discovery/export commands
- installation from source and release binaries for approved platforms
- Agent Skills guide updated with all available operations
- shell-safe examples for Pi, Claude Code, Codex, and generic agents
- bounded diagnostics on stderr
- compatibility tests across Linux and macOS
- reproducible release checklist and checksums

### Out of scope

- allowing agents to mutate source resumes automatically
- hidden prompts or built-in model-provider integration
- remote execution service
- MCP unless a documented consumer cannot use CLI/stdin

### Acceptance

- an agent can discover capabilities, validate input, invoke every operation, and parse results without reading Rust internals
- stdout is machine-clean in JSON modes
- errors and exit statuses are documented and tested
- installation does not execute unreviewed network code beyond standard package retrieval
- no source payload appears in logs

## Phase 6 — Swift binding boundary

### Goal

Expose stable core operations to a separate SwiftUI macOS application with an iOS-compatible path.

### Prerequisite

Phases 1–5 contracts required by the app are stable and versioned.

### Scope

- evaluate UniFFI against current stable Rust/Swift support
- narrow FFI facade using owned primitive/record types
- Rust-to-Swift error mapping
- XCFramework build for Apple Silicon macOS, iOS device, and iOS simulator
- Swift Package wrapper and minimal Swift smoke application
- deterministic parity tests across Rust and Swift calls
- release/checksum integration

### Out of scope

- SwiftUI product features
- persistence or document pickers
- App Store distribution
- cloud sync or accounts

### Acceptance

- the same fixture produces equivalent Rust CLI and Swift binding output
- no platform logic moves into `career-core`
- unsafe/FFI code is isolated, documented, and reviewed
- Apple artifacts are reproducible and version aligned

## Phase 7 — Optional concrete adapters

### Goal

Add only adapters justified by demonstrated consumers.

### Candidate work

- Python bindings for a concrete non-Django consumer
- MCP-over-stdio adapter if CLI integration is insufficient
- WASM build if a local browser consumer exists
- package-manager distribution and signed binaries

Each candidate requires its own design note, threat model, maintenance owner, and explicit approval. No adapter is automatically part of the roadmap.
